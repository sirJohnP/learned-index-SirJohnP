# Обученные индексы

## Задание

Отсортированный массив различных ключей `keys[0] < keys[1] < ... < keys[n - 1]` задаёт отображение ключа в его позицию. Индекс приближает это отображение моделью: `predict(key)` предсказывает позицию с ошибкой не больше `maxError()`, а `lower_bound(key)` находит точную позицию поиском в окне вокруг предсказания.

Требуется реализовать классы из раздела «Классы для реализации» так, чтобы каждый индекс выполнял контракт интерфейса `Index`.

## Запуск

```sh
bash run.sh
```

Требуется JDK 26. Скрипт собирает проект, копирует `hw-template.jar` в корень репозитория и запускает его с конфигурацией `config.properties`; файлы SOSD читаются из корня репозитория. Результат выводится в консоль и в файл `results.txt`. Чтобы включить сохранение графиков предсказаний в каталог `out.path`, запустите `bash run.sh --plot`. На график добавляются успешные индексы с `maxError() > 0`; если таких индексов для набора данных нет, PDF не создаётся.

Каждая строка таблицы строится, проверяется и замеряется в отдельной JVM с Epsilon GC и кучей 8 ГиБ.

| столбец | значение |
|---|---|
| `build ms` | время `build` |
| `maxErr` | `maxError()` |
| `size KiB` | `sizeInBytes()`, в КиБ |
| `min iter ms` | минимальное время целой итерации из 100 000 запросов среди 10 измеряемых итераций, мс |
| `max iter ms` | максимальное время целой итерации среди тех же 10 итераций, мс |
| `mean iter ms` | среднее время целой итерации по тем же 10 итерациям, мс |
| `throughput/s` | число запросов в секунду: `100 000 * 1000 / mean iter ms` |

Строка `not implemented` означает, что индекс бросил `UnsupportedOperationException`; строка `failed: ...` — другое исключение, нарушение контракта, исчерпание кучи или работу дольше 10 минут.

### config.properties

Каждый ключ, кроме `out.path`, принимает список значений через `;`. Все комбинации `data.*` дают отдельные таблицы. В каждой таблице запускаются индексы из `index.types`: поисковые — по одному запуску, кусочно-линейные — для каждого `index.err`, нейросетевые — для всех комбинаций параметров `net.*`.

Для `data.keyset` ниже перечислены 32-битные наборы, подходящие для интерфейса `Index`. Полный список наборов определён в `me.index.config.parameters.enums.Keyset`. Конфигурация также принимает 64-битные наборы, но стенд работает с ними только тогда, когда все ключи после загрузки помещаются в `int`.

| ключ | значения | по умолчанию |
|---|---|---|
| `data.keyset` | `_gauss_int32`, `_log_norm_int32`, `_books_200M_uint32` (файл SOSD) | обязателен |
| `data.size` | `_1e4`, `_1e5`, `_1e6`, `_1e7`, `_max` (200 млн; недоступен для 32-битных синтетических наборов) | обязателен |
| `data.seed` | целое | `42` |
| `index.types` | `_binary`, `_exponential`, `_interpolation`, `_pla_greedy`, `_pla_spline`, `_pla_convex`, `_net_sigmoid`, `_net_relu`, `_net_leaky_relu`, `_net_softsign` | обязателен |
| `index.err` | `_0`, `_1`, `_2`, `_4`, `_8`, `_16`, `_32`, `_64` | `_32` |
| `net.layers` | размеры скрытых слоёв через запятую или `none` | `4,4` |
| `net.train.loss` | `_squared`, `_absolute`, `_huber(δ)`; `_huber` без параметра означает `δ = 0.02` | `_squared` |
| `net.train.rate` | число больше 0 | `0.05` для `_squared`, `0.005` для `_absolute`, `0.5` для `_huber` |
| `net.train.epochs` | целое больше 0 | `100` |
| `net.train.batch.size` | целое больше 0 | `32` |
| `net.train.seed` | целое | `42` |
| `out.path` | каталог | `out` |

## Интерфейс Index

```java
public interface Index {
    void build(int[] keys);

    int predict(int key);

    int lower_bound(int key);

    String id();

    int maxError();

    long sizeInBytes();
}
```

`n` — длина массива, переданного в `build`; позиция — индекс в этом массиве.

| метод | контракт |
|---|---|
| `build(keys)` | Строит индекс. `keys` строго возрастает и содержит не меньше двух ключей, иначе `IllegalArgumentException` (проверка — `Sorted.checkKeys`). Индекс может хранить ссылку на `keys`. Вызывается один раз, до остальных методов, кроме `id()`. |
| `predict(key)` | Возвращает позицию из `[0, n - 1]`. Для каждого `i`: `abs(predict(keys[i]) - i) <= maxError()`. |
| `lower_bound(key)` | Возвращает наименьшее `i`, при котором `keys[i] >= key`, или `n`, если такого `i` нет. Точен для любого `int`, в том числе для ключа, которого нет в массиве. Для уточнения предсказания используется `Sorted.lowerBoundNear`; `PlaIndex` передаёт границы и измеренную ошибку выбранного сегмента. |
| `id()` | Возвращает имя индекса в таблице и на графике. Не зависит от `build`. |
| `maxError()` | Возвращает `max abs(predict(keys[i]) - i)` по всем `i` или верхнюю оценку этой величины. |
| `sizeInBytes()` | Возвращает расчётный объём данных индекса, используемых при поиске: элементов массивов и параметров сегментов. Не включает исходный массив `keys`, заголовки объектов и массивов, ссылки, служебные скалярные поля и данные, нужные только для построения. Для `PlaIndex` учитываются максимальный ключ, начальная позиция, измеренная ошибка и два коэффициента каждого сегмента — 28 байт на сегмент; дополнительно учитываются элементы radix-таблицы, если она построена. |

`Sorted.lowerBoundNear` ограничивает предсказание `p` допустимым диапазоном и ищет среди элементов полуинтервала `[p - e, p + e + 1)`, обрезанного по границам этого диапазона. При `e <= 32` поиск линейный от `p` в нужную сторону, иначе — бинарный. Если проверки границ показывают, что ответ находится вне окна, выполняется бинарный поиск в соответствующей оставшейся части диапазона. Для `PlaIndex` диапазон — выбранный сегмент, а `e` — его измеренная ошибка; для остальных индексов используются весь массив и `maxError()`. При соблюдении контракта точности расширение поиска требуется только для отсутствующих ключей. Правой границей полуинтервала также может быть правильная позиция вставки.

Бенчмарк проверяет контракт на всех 30 пачках по 100 000 запросов после завершения измерений. Для всех запросов проверяются точность `lower_bound` и диапазон `predict`; ограничение ошибки `maxError()` проверяется только на существующих ключах. Для поисковых индексов на всех запросах дополнительно требуется `predict(key) == min(lower_bound(key), n - 1)`. После замеров для всех десяти измеряемых пачек также проверяются соседние значения `k - 1`, `k + 1`, если они помещаются в `int`, и границы `Integer.MIN_VALUE`, `Integer.MAX_VALUE`. Обнаруженное нарушение делает строку `failed`.

## Классы для реализации

Ниже перечислены классы, которые требовалось реализовать в исходном задании, и требования к ним. В этой версии все перечисленные классы реализованы.

### me.index.task.isearch

Даны `Searches` (соответствие `index.types` классам) и `BinarySearchIndex`. Индексы пакета предсказывают позицию точно: `predict(key)` равен `min(lower_bound(key), n - 1)`, `maxError()` равен `0`, `sizeInBytes()` равен `0`.

| класс | способ вычисления `predict` | `id()` |
|---|---|---|
| `ExponentialSearchIndex` | экспоненциальный поиск: правая граница удваивается, начиная с `1`, и ограничивается `n - 1`; расширение заканчивается при `keys[b] >= key` или достижении конца массива, затем выполняется бинарный поиск в полученном интервале | `exponential` |
| `InterpolationSearchIndex` | интерполяционный поиск: следующая позиция в интервале `[lo, hi]` вычисляется линейной интерполяцией между `keys[lo]` и `keys[hi]` | `interpolation` |

### me.index.task.isegment

Даны `Window`, `Windows` (соответствие `index.types` стратегиям), `GreedyWindow` и `PlaIndex`. `PlaIndex` разбивает массив на сегменты методом `Window.split` и хранит для каждого сегмента его максимальный ключ, начальную позицию, прямую и измеренную ошибку; `predict` находит сегмент бинарным поиском по максимальным ключам и вычисляет позицию по прямой сегмента.

Стратегия разбиения реализует интерфейс `Window`; `Window.split` вызывает её для каждого сегмента.

| метод | контракт |
|---|---|
| `init_skip(key, err)` | Начинает сегмент с ключа `key` и сбрасывает состояние предыдущего сегмента. Возвращает `0` или `1` — сколько первых ключей сегмента входит в него без вызова `can_expand`; при `0` метод `can_expand` вызывается и для `key` с `pos = 0` и должен вернуть `true`. |
| `can_expand(key, pos, err)` | `key` — следующий ключ, `pos` — его позиция относительно начала сегмента. `true` — ключ добавлен в сегмент; `false` — сегмент закрыт, ключ начинает следующий сегмент. |
| `get_result()` | Возвращает прямую сегмента `{slope, intercept}`. Позиция ключа относительно начала сегмента по этой прямой — `Maths.predict(slope, intercept, key)`, то есть `max((int) (slope * key + intercept), 0)`. |

В точной арифметике прямая допустима для сегмента, если на каждом его ключе `slope * key + intercept` лежит в `[pos - err, pos + err]`, где `pos` — позиция относительно начала сегмента, `err` — значение `index.err`. При вычислениях в `double` округление может увеличить ошибку. `Window.split` проверяет непустоту сегмента, форму результата и конечность коэффициентов. `PlaIndex` измеряет фактическую целочисленную ошибку каждого сегмента и использует её при поиске. Если максимальная измеренная ошибка превышает `index.err`, бенчмарк выводит предупреждение, а не исключение.

| класс | правило продления сегмента |
|---|---|
| `RSpline` | первые два ключа принимаются без проверки коридора; каждый следующий ключ принимается, если прямая через первый и этот ключ проходит строго внутри текущего коридора допустимых наклонов. При принятии ключа коридор сужается по его допуску `pos ± err`. Результат — прямая через первый и последний принятый ключ; для одиночного сегмента — нулевая прямая |
| `CHT` | сегмент продлевается, пока существует любая допустимая прямая; множество допустимых прямых задаётся верхней и нижней выпуклыми оболочками, вычисления выполняются точно в `Int128` и `Frac128` |

В точной арифметике при одинаковом допуске сегмент `CHT`, начатый с того же ключа, не короче допустимого сегмента `RSpline` или `GreedyWindow`. Между длинами сегментов `RSpline` и `GreedyWindow` общего порядка нет.

### me.index.task.inet

Даны `NetIndex`, `Models` (соответствие `index.types` моделям), `Init`, интерфейсы `Model` и `Loss`, классы `SigmoidNet` и `SquaredLoss`. `NetIndex` обучает модель на парах `x = 2 * (keys[i] - keys[0]) / (keys[n - 1] - keys[0]) - 1`, `y = i / (n - 1)` и предсказывает позицию `round(model.predict(x) * (n - 1))`, ограниченную отрезком `[0, n - 1]`.

**Модели.** Конструктор — `(int[] layerSizes, double learningRate, int batchSize, Loss loss, Random rnd)`, где `layerSizes = [1, h1, ..., hk, 1]`. Сеть полносвязная: скрытые слои применяют функцию активации, выходной слой линейный. Начальные веса слоя — нормальные со стандартным отклонением `Init.scale(fanIn, fanOut)`, смещения — нули.

| метод | контракт |
|---|---|
| `predict(x)` | прямой проход сети |
| `train(xs, ys, epochs)` | `epochs` эпох стохастического градиентного спуска: в каждой эпохе порядок примеров перемешивается генератором `rnd`, веса обновляются по среднему градиенту мини-батча из `batchSize` примеров с шагом `learningRate`; возвращает среднеквадратичную ошибку `predict` на `(xs, ys)` после обучения |
| `id()` | имя активации, `/` и `loss.id()` |
| `sizeInBytes()` | `8 *` (число весов, смещений и элементов буферов, которые читает `predict`) |

`predict` и обработка мини-батча не выделяют память: веса, смещения и буферы создаются в конструкторе. `SigmoidNet` обновляет веса после каждого примера, игнорирует размер батча и также переиспользует вычислительные буферы.

| класс | активация `f(z)` | производная `f'(z)` | масштаб инициализации | `id()` |
|---|---|---|---|---|
| `ReluNet` | `max(0, z)` | `z > 0 ? 1 : 0` | `Init.HE` | `relu/...` |
| `LeakyReluNet` | `z > 0 ? z : 0.01 * z` | `z > 0 ? 1 : 0.01` | `Init.HE` | `leaky_relu/...` |
| `SoftsignNet` | `z / (1 + abs(z))` | `1 / (1 + abs(z))^2` | `Init.XAVIER` | `softsign/...` |

**Функции потерь.** `e = predicted - target`.

| класс | `value` | `gradient` | `id()` |
|---|---|---|---|
| `AbsoluteLoss` | `abs(e)` | `signum(e)` | `absolute` |
| `HuberLoss(δ)` | `e^2 / 2` при `abs(e) <= δ`, иначе `δ * (abs(e) - δ / 2)` | `e` при `abs(e) <= δ`, иначе `δ * signum(e)` | `huber(δ)` |

Конструктор `HuberLoss` бросает `IllegalArgumentException`, если `δ` не является конечным положительным числом.

### Актуальная структура и запуск

Разделы выше сохраняют исходную постановку задания. В этой версии вместо прежних `Fork`, `Worker`, `Row`
используется следующая структура; приведённые здесь уточнения описывают текущее поведение.

- `Main` разбирает `[--plot] [sosd-data-dir]`, читает `config.properties` из текущего каталога,
  перебирает `Config.dataParams()` и `Config.indexParams()`, выводит таблицы и сохраняет графики.
- `Context.load` генерирует ключи либо открывает и закрывает файл SOSD. `Context.intKeys` проверяет диапазон `int`.
- `Benchmark` — вторая точка входа для одного эксперимента с явно заданными параметрами.
  `Benchmark.fork` запускает её в отдельной JVM через `libs.execute.JvmRunner`.
- `libs.execute.TempDirectory` управляет временным каталогом. `libs.execute.parameters` содержит
  `BenchmarkArguments`, `BenchmarkSummary` и `BenchmarkResult`: аргументы, сводку и полный результат с предсказаниями.
  `BenchmarkQueries` заранее готовит последовательность случайных пачек запросов и эталонные позиции вставки.
- `libs.view.StringReport` формирует текст, `PdfReport` оформляет графики эксперимента, `Plot` рисует их.
  `libs.view.pdf` содержит низкоуровневые `Document`, `Page` и `Font`.
- `libs.math.KeyGenerator` генерирует наборы, `libs.io.SosdReader` читает бинарный формат SOSD.

Графики выключены по умолчанию. При `--plot` строятся предсказания успешных индексов с ненулевой измеренной ошибкой вместе с истинными позициями. Если все успешные индексы точные, PDF для набора не создаётся.

`PdfReport` отображает не более 100 000 ключей: большие наборы равномерно прореживаются по позициям с сохранением первого и последнего ключей. Истинные позиции и все предсказания используют одни и те же выбранные ключи; позиции остаются рангами в исходном массиве. Прореживание касается только графика, обучение и проверки выполняются на полном наборе данных.

До построения индекса для поиска создаются 30 пачек по 100 000 запросов. Один генератор `Random` с seed `data.seed` последовательно формирует первые 20 пачек для прогрева и следующие 10 для измерений; состояние генератора между пачками не сбрасывается. Сортировка исходных ключей проверяется один раз при подготовке всей последовательности. Все запросы в прогревочных и измеряемых пачках относятся к существующим ключам. Для каждого запроса равномерно выбирается позиция массива с возвращением; она же служит эталонным ответом. Последовательность сразу случайная, дополнительное перемешивание не требуется. Проверки отсутствующих соседних значений и крайних ключей выполняются отдельно после замеров.

В каждой итерации используется следующая пачка. Отдельные значения могут повторяться внутри пачек и между ними; уникальность запросов не требуется. Генерация и проверки не выполняются между измеряемыми итерациями. Все 30 пачек проверяются после измерений. Для всех индексов с одинаковым набором данных и seed последовательности запросов совпадают. Массивы запросов и эталонных позиций занимают около 24 МБ. Новые пачки уменьшают повторение конкретных обращений, но не делают эксперимент измерением полностью холодного кеша.

`System.nanoTime()` вызывается до и после целого раунда: внутри измеряются вызовы `lower_bound`, цикл и суммирование найденных позиций в контрольную сумму. Отдельный запрос таймером не оборачивается. Генерация запросов, вычисление эталонных ответов и проверки не входят в измеряемое время.

Если длительности десяти измеряемых итераций равны `T1, ..., T10` наносекунд, то `min iter ms = min(Ti) / 1e6`, `max iter ms = max(Ti) / 1e6`, `mean iter ms = sum(Ti) / 10 / 1e6`. Все три столбца показывают время целой пачки из 100 000 запросов. Двадцать прогревочных итераций в эти показатели не входят.

`throughput/s = 100 000 * 1e9 / (sum(Ti) / 10)`. Он рассчитывается из неокруглённого среднего времени, а не из лучшего раунда и не как среднее обратных величин; выводится с округлением до целого запроса в секунду. При неположительном или неконечном времени выводится `-`. Чтобы получить среднее время одного запроса в наносекундах, разделите среднее время итерации в наносекундах на 100 000. Контрольная сумма включает результаты всех 30 пачек: 20 прогревочных и 10 измеряемых раундов.

Предсказания для графика вычисляются в дочерней JVM после измерений и проверок отсутствующих ключей. Родительский `Main` добавляет прореженные серии между запусками индексов; отрисовка и запись PDF происходят после всех индексов текущего набора данных. Эти действия не входят в `min iter ms`, `max iter ms`, `mean iter ms` и `throughput/s`, но увеличивают общее время и расход памяти запуска.

`Plot` настраивается до первого `write`. После него изменение настроек или добавление слоёв вызывает `IllegalStateException`; повторный `write` сохраняет тот же график.

Примеры запуска из корня репозитория:

```sh
./mvnw package
java -jar target/hw-template.jar
java -jar target/hw-template.jar --plot /path/to/SOSD
bash run.sh --plot /path/to/SOSD
```

`run.sh` сначала выполняет чистую сборку с тестами и передаёт аргументы в `Main`.
Неверные аргументы CLI завершают `Main` с кодом 2, ошибка конфигурации или чтения данных — с кодом 1.
Ошибка отдельного индекса отображается как строка `failed`; остальные эксперименты продолжаются.
Временный `result.bin` передаёт сводку и, только при включённых графиках, предсказания.
После чтения результата файл удаляется; при завершении процесса дочерняя JVM останавливается перед очисткой каталога.

Конфигурация использует грамматику Java Properties: `key=value`, комментарии `#`/`!`, продолжение строки через `\`.
Внутри значения `;` разделяет варианты, внутри `net.layers` запятая разделяет размеры слоёв.
Например, `data.seed=42;43`, `index.err=_0;_8`, `net.layers=none;4,4`.
Пробелы вокруг вариантов удаляются; пустые элементы внутри списка запрещены.
Отсутствующее или пустое значение необязательного свойства означает значение по умолчанию.
Неизвестные имена свойств отклоняются; повторные значения списка сохраняются.
Повторное объявление одного свойства заменяет предыдущее по правилам Java Properties.
`out.path` принимает один путь; точка с запятой внутри пути не поддерживается.
При нескольких seed данных имя PDF включает seed, чтобы разные наборы не перезаписывали друг друга.

### Поиски и функции потерь

`ExponentialSearchIndex` и `InterpolationSearchIndex` выполняют точный поиск позиции. Удвоение границы экспоненциального поиска, разности ключей и произведение при интерполяции вычисляются в `long`, чтобы избежать переполнения `int`. `AbsoluteLoss` и `HuberLoss` реализуют значения и градиенты из постановки; параметр Huber проверяется на конечность и положительность.

### Сегментация

`CHT` использует два массива-стека выпуклых оболочек и точные вычисления в `Int128` и `Frac128`. Он принимает равенство на границе допуска, в том числе при `err = 0`. Стеки расширяются только при заполнении и переиспользуются между сегментами; суммарная работа с оболочками линейна по числу ключей. `PlaIndex` измеряет ошибку сразу после завершения каждого сегмента последовательным проходом по его ключам; суммарная работа измерения ошибки также линейна. Арифметика `Int128` имеет фиксированную разрядность, а реализация рассчитана на ключи `int` и позиции в `int[]`. При прямом вызове `CHT.can_expand` с `Long.MIN_VALUE` выбрасывается `IllegalArgumentException` до операции `-key`, чтобы не допустить переполнения. `Integer.MIN_VALUE` поддерживается, поскольку отрицание выполняется уже в `long`.

`RSpline` реализует жадный `GreedySplineCorridor`: после первых двух ключей прямая через первый и очередной ключ должна лежать строго внутри текущего коридора. При принятии ключа коридор сужается по его допуску `pos ± err`; при отказе результатом остается прямая через первый и последний принятый ключ.

Строгие проверки ориентации сохранены: при `err = 0` третья коллинеарная точка закрывает сегмент. От этой жадной стратегии не требуется максимальная длина сегмента или минимальное число сегментов. Здесь она адаптирована к `Window` с неперекрывающимися сегментами; общий узел соседних участков непрерывного сплайна не используется. Ускорение выбора сегмента через radix-таблицу реализовано отдельно в `PlaIndex` и доступно всем трём вариантам сегментации. Основной цикл работает со скалярами `double`, без деления и выделения памяти. Исходный алгоритм: [RadixSpline](https://github.com/learnedsystems/RadixSpline), реализация коридора — [builder.h](https://github.com/learnedsystems/RadixSpline/blob/master/include/rs/builder.h).

`GreedyWindow` фиксирует прямую через первые две точки сегмента и принимает следующие ключи, пока их вещественная ошибка относительно этой прямой не превышает `err`. Прямая при расширении не меняется. При отказе ключ начинает новый сегмент; для одиночного сегмента возвращается нулевая прямая.

В точной арифметике сегмент CHT, начатый с того же ключа, не короче допустимого сегмента RSpline или GreedyWindow. Между длинами сегментов RSpline и GreedyWindow общего порядка нет. Например, для `[0, 10, 30, 31, 32]` при `err = 1` GreedyWindow принимает все ключи с наклоном `0.1`, а RSpline отвергает последний ключ.

### Точность и поиск

`PlaIndex` хранит начальные позиции, максимальные ключи, ошибки и коэффициенты сегментов в отдельных массивах примитивов `int[]` и `double[]`. Массивы заполняются при построении, растут по мере необходимости и в конце обрезаются до числа сегментов. Поиск не выделяет память.

`PlaIndex` ускоряет выбор сегмента с помощью radix-таблицы: старшие биты разности `key - keys[0]` задают диапазон поиска в массиве максимальных ключей сегментов. Разность вычисляется в `long`, поэтому поддерживается весь диапазон `int`. При 16 сегментах и меньше остаётся обычный бинарный поиск. Для больших индексов размер таблицы выбирается по числу сегментов и диапазону ключей, но не превышает 16 385 элементов `int` — 64 КиБ плюс 4 байта. Таблица строится одним проходом по сегментам и границам диапазонов. Если один диапазон содержит больше половины границ сегментов, таблица не сохраняется и используется обычный бинарный поиск: на сильно перекошенных данных дополнительный уровень может замедлять поиск. Внутри диапазона с числом кандидатов до 8 используется линейный поиск, иначе бинарный. Пустые диапазоны также обрабатываются: результатом может быть первый сегмент следующего диапазона. Алгоритм построения сегментов и уточнение позиции по фактической ошибке не меняются.

Математически допустимая прямая проходит через полосы `[pos - err, pos + err]`. При точном вычислении усечение до целой позиции сохраняет эту границу ошибки. Но коэффициенты результата хранятся в `double`: округление и вычисление `slope * key + intercept` могут изменить фактическую ошибку, особенно при `err = 0`.

`Window.split` проверяет непустоту сегмента, форму результата и конечность коэффициентов.
Фактическую целочисленную ошибку на всех ключах каждого сегмента измеряет и сохраняет `PlaIndex`; превышение заданного `err`
сообщает `Benchmark.warning` через переданный поток диагностики. Причиной могут быть как ошибка сегментации,
так и округление: само предупреждение их не различает. Превышение допуска не заменено исключением. `PlaIndex.maxError()` сообщает максимум ошибок сегментов, а точный поиск использует ошибку выбранного сегмента. При ошибке не больше 32 `Sorted.lowerBoundNear` ищет линейно от предсказания, иначе — бинарно в окне ошибки. При необходимости поиск продолжается бинарно в оставшейся части выбранного сегмента. Сегмент определяется один раз на запрос; его границы гарантируют наличие правильной позиции для любого ключа не больше максимального ключа массива. Для большего ключа `PlaIndex.lower_bound` сразу возвращает длину массива. Безусловные сдвиги прямой на `0.5` и точное запасное вычисление коэффициентов при поиске не используются.

Например, `[0, 49]` при `err = 0` дает математически точную прямую CHT `x / 49`, но после округления коэффициента и усечения ошибка предсказания достигает 1. `PlaIndex` учитывает эту ошибку и правильно возвращает `lower_bound(49) = 1`.

### Нейронные модели

`ReluNet`, `LeakyReluNet` и `SoftsignNet` используют общий движок `MiniBatchNet`. У них `predict` и обработка мини-батча не выделяют память: веса, смещения и рабочие буферы создаются в конструкторе. Все четыре модели переиспользуют массив порядка примеров между вызовами `train`. Он выделяется при первом обучении на непустой выборке и расширяется только при увеличении её размера; при уменьшении используется только активная часть. Перед каждым вызовом обучения порядок заново инициализируется. После подготовки достаточного буфера `predict` и `train` на корректных данных не выделяют память со стандартными `Random` и функциями потерь.

Веса внутри батча не изменяются, последний неполный батч усредняется по фактическому числу примеров. Производная вычисляется по сохраненной активации, без отдельного массива входов активации; для Softsign это `(1 - abs(a))^2`. Размер модели учитывает веса, смещения и буферы активаций; обучающие градиенты и ошибки обратного прохода исключены.

`MiniBatchNet` проверяет форму слоев, положительность их размеров и размера батча, конечность и положительность шага, наличие `loss` и `rnd`. Обучающие массивы должны иметь одинаковую длину, число эпох — быть неотрицательным. Для непустой выборки при нуле эпох возвращается текущая MSE без обучения; для пустой — `NaN`.

`SigmoidNet` сохраняет исходное обучение по одному примеру и игнорирует размер батча. Прямой и обратный проходы используют постоянные буферы, созданные в конструкторе; временные массивы на каждом примере больше не создаются. Размер модели теперь включает буферы активаций. В отличие от новых моделей, при нуле эпох он возвращает `NaN`; штатная конфигурация допускает только положительное число эпох.

В `NetIndex.predict` результат `Math.round` ограничивается допустимым диапазоном до сужения из `long` в `int`. Это предотвращает переполнение при больших предсказаниях. Значение `NaN` приводит к явному исключению.

### Проверки стенда

Помимо исходных проверок, `Benchmark` проверяет диапазон `predict` на запросах `k - 1`, `k + 1`, `Integer.MIN_VALUE` и `Integer.MAX_VALUE`. Для поисковых индексов дополнительно требуется `predict(key) == min(lower_bound(key), n - 1)`, нулевая ошибка и нулевой размер. Отрицательные значения `maxError()` и `sizeInBytes()` отклоняются. Проверки выполняются вне измеряемых раундов. Успешный прогон стенда сам по себе не доказывает корректность сегментации или градиентов сети на всех входах.

Стратегии `Window` хранят изменяемое состояние в экземплярах `enum`, а новые сети переиспользуют рабочие буферы. Одновременные построения с одной стратегией или параллельные вызовы одной модели не поддерживаются. Штатный стенд использует отдельную JVM для каждой строки.

### Беззнаковые ключи SOSD

Загрузчик переводит беззнаковые ключи в знаковый диапазон той же разрядности: `uint32` — сдвигом на `−2^31`, `uint64` — сдвигом на `−2^63`. Для прочитанного 64-битного представления второй сдвиг реализован как `key ^ Long.MIN_VALUE`. Преобразование сохраняет порядок, различимость ключей и математические расстояния между ними. Оно применяется ко всем SOSD-наборам; флаги `needShift` и `needPlusOne` удалены. Заголовок с числом элементов и синтетические знаковые данные не сдвигаются.

`_books_200M_uint32` поддерживает весь исходный диапазон `[0, 2^32 − 1]`. Индексы, запросы стенда и графики используют уже сдвинутые ключи; внешний запрос по исходному беззнаковому ключу нужно преобразовать тем же способом. Загрузчик поддерживает весь диапазон `uint64` в `long[]`, однако интерфейс `Index` и стенд по-прежнему работают с `int[]`: поиск по произвольным 64-битным ключам не реализован, и значения вне диапазона `int` отклоняются в `Context.intKeys()`.

| Данные и конфигурация | Комбинации параметров, значения по умолчанию и неверные настройки; воспроизводимые, отсортированные и уникальные синтетические ключи; все SOSD-форматы, крайние `uint32`/`uint64`, дубликаты, усечённые файлы и неверные заголовки, закрытие файлов. |
| Стенд и PDF | Времена итераций и throughput с управляемым таймером; 30 воспроизводимых пачек запросов, равномерность выбора позиций и контрольные суммы. Дочерние JVM, полный путь `Main → Benchmark.fork → Benchmark.main`, CLI, сериализация, очистка временных файлов, таймаут и прерывание процесса, ошибки передачи вывода и нарушения контракта индекса. PDF: текст, байтовые смещения `xref`, повторное сохранение, варианты графиков, отсутствие PDF при нулевой ошибке, лимит 100 000 точек, исходные ранги и соответствие предсказаний. |

Проверки студенческих алгоритмов не зависят от названий их приватных полей, расположения весов и устройства оболочек. Для сетей задаётся управляемая инициализация через переданный `Random`, а обучение проверяется по наблюдаемым предсказаниям и независимым численным градиентам. Перемешивание проверяется без требования конкретного алгоритма shuffle. Рефлексия остаётся только в проверках общих для всех репозиториев `PlaIndex` и `Plot`.

Для RSpline принимаются оба варианта: максимальный допустимый коридор через первую точку из первоначального задания и жадное правило эталона. На границе коридора учитывается погрешность сравнения до нескольких ULP. В обоих случаях возвращённая прямая должна проходить через первую точку и укладываться в eps-коридор с учётом округления `double`. Корректный целочисленный `predict` сам по себе не заменяет проверку этого геометрического требования. CHT проверяется на точную допустимость сегмента, но без требования конкретных внутренних коэффициентов или состояния оболочек после отказа добавить точку.

Функции потерь создаются внутри каждого сценария: незавершённый `HuberLoss` не мешает запуску остальных тестов. Модели, функции потерь, алгоритмы и eps разделены параметрами JUnit. `sosdTranslatesUnsignedBoundariesAndDeduplicates` проверяет только загрузчик; `indexesHandleFullIntRange` отдельно проверяет 28 вариантов индексов. Сообщения проверок поиска содержат запрошенный ключ. Сквозные проверки стенда используют общие готовые `binary` и `pla_greedy`, чтобы незавершённый студенческий алгоритм не маскировал состояние инфраструктуры.

Проверки некорректного ввода, пустой выборки и повторного обучения помечены `@Tag("robustness")`, проверки выделений памяти — `@Tag("allocation")`. Они включены в обычный запуск, но являются дополнительной диагностикой: их падение нужно сопоставлять с требованиями первоначального задания, а не автоматически считать ошибкой студента. В частности, исходный предоставленный Sigmoid мог выделять память при обучении. Число упавших параметризованных сценариев не равно числу независимых дефектов: одна незавершённая функция потерь влияет на несколько проверок моделей.

Тесты выполняются последовательно: стратегии `Window` используют общие изменяемые экземпляры. Каждый сценарий ограничен 30 секундами, основные проверки поиска — 5 секундами. JVM Surefire получает до 512 МиБ, прямые запуски `Benchmark` — до 256 МиБ. **Сквозной тест `Main` использует штатный `Benchmark.fork`: дочерние JVM запускаются последовательно, каждая получает 8 ГиБ с предварительным выделением памяти. Для одного seed запускаются две JVM, для двух — четыре.** Для полного запуска нужна свободная память под эту JVM и Maven/JUnit. Это проверка работоспособности, а не сравнение производительности.

Временные каталоги создаёт и удаляет JUnit через `@TempDir`; настоящие файлы SOSD не нужны. Случайные данные имеют фиксированные seed. Проверка открытых файлов использует Unix-счётчик, проверки выделений памяти — `com.sun.management.ThreadMXBean`; на неподдерживаемой платформе соответствующие сценарии пропускаются.

Успешный Maven-лог без `-q` содержит:

```text
Tests run: 207, Failures: 0, Errors: 0, Skipped: 0
...
BUILD SUCCESS
```

Отчёты — в `target/surefire-reports`. Без упаковки: `./mvnw test`. Один сценарий:

```sh
./mvnw -Dtest=AllTests#segmentsRespectExactGeometryAndLookup test
```

Проверка перед публикацией: `./mvnw clean package`. `run.sh` также вызывает `package`, но его флаг `-q` сокращает Maven-лог. Отдельных скриптов запуска тестов нет; обёртки `mvnw` и `mvnw.cmd` стандартные, JUnit имеет область зависимости `test` и не включается в рабочий JAR. Первичная загрузка зависимостей требует сети; сами тесты не обращаются к внешним сервисам.

Набор проверяет контракты и граничные сценарии всех пакетов, но не доказывает отсутствие любых ошибок. Не моделируются исчерпание памяти, гигантские массивы, многопоточный доступ к индексам и поиск по произвольным `long` — интерфейс `Index` принимает `int`.

## SOSD

Из корня проекта выполните:

```sh
bash download.sh
```

Скрипт скачивает и распаковывает наборы SOSD в папку `data/`; сейчас включён `books_200M_uint32`. Для загрузки нужны `wget` и `zstd`.

В `config.properties` выберите набор и размер, например:

```properties
data.keyset = _books_200M_uint32
data.size = _1e7
```

Затем запустите:

```sh
bash run.sh ./data
```
